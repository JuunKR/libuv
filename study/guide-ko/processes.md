# Processes

libuv는 플랫폼 차이를 추상화하고 스트림 또는 명명된 파이프를 사용하여 자식 프로세스와
통신할 수 있도록 하는 상당한 자식 프로세스 관리를 제공합니다.

Unix의 일반적인 관용구는 모든 프로세스가 한 가지를 하고 잘하는 것입니다. 이러한 경우
프로세스는 종종 작업을 달성하기 위해 여러 자식 프로세스를 사용합니다(셸에서 파이프를
사용하는 것과 유사). 메시지가 있는 다중 프로세스 모델은 스레드와 공유 메모리가 있는
모델보다 추론하기 쉬울 수 있습니다.

이벤트 기반 프로그램에 대한 일반적인 반박은 현대 컴퓨터의 여러 코어를 활용할 수 없다는
것입니다. 다중 스레드 프로그램에서 커널은 스케줄링을 수행하고 다른 스레드를 다른 코어에
할당하여 성능을 향상시킬 수 있습니다. 하지만 이벤트 루프에는 스레드가 하나만 있습니다.
해결 방법은 대신 여러 프로세스를 시작하는 것일 수 있으며, 각 프로세스는 이벤트 루프를
실행하고 각 프로세스가 별도의 CPU 코어에 할당됩니다.

## Spawning child processes

가장 간단한 경우는 프로세스를 시작하고 종료 시점을 알고 싶을 때입니다. 이것은
``uv_spawn``을 사용하여 달성됩니다.

```c
// spawn/main.c
// (코드 예제는 원본 참조)
```

``uv_process_t`` 구조는 핸들 역할만 하며 모든 옵션은 ``uv_process_options_t``를
통해 설정됩니다. 단순히 프로세스를 시작하려면 ``file`` 및 ``args`` 필드만 설정하면
됩니다. ``file``은 실행할 프로그램입니다. ``uv_spawn``이 내부적으로 :man:`execvp(3)`를
사용하므로 전체 경로를 제공할 필요가 없습니다. 마지막으로 기본 규칙에 따라 **인수 배열은
인수 수보다 하나 더 커야 하며 마지막 요소는 NULL**이어야 합니다.

``uv_spawn`` 호출 후 ``uv_process_t.pid``는 자식 프로세스의 프로세스 ID를 포함합니다.

종료 콜백은 *종료 상태*와 종료를 유발한 *시그널* 유형과 함께 호출됩니다.

종료 콜백 전에 ``uv_close``를 호출하지 않는 것이 중요합니다.

종료 후 프로세스 감시자를 닫는 것이 **필수**입니다.

## Changing process parameters

자식 프로세스가 시작되기 전에 ``uv_process_options_t``의 필드를 사용하여 실행 환경을
제어할 수 있습니다.

### Change execution directory

``uv_process_options_t.cwd``를 해당 디렉토리로 설정합니다.

### Set environment variables

``uv_process_options_t.env``는 프로세스의 환경 변수를 설정하는 데 사용되는
``VAR=VALUE`` 형식의 문자열로 구성된 null로 끝나는 배열입니다. 부모(이) 프로세스에서
환경을 상속하려면 이것을 ``NULL``로 설정합니다.

### Option flags

``uv_process_options_t.flags``를 다음 플래그의 비트 OR로 설정하면 자식 프로세스 동작이
수정됩니다:

* ``UV_PROCESS_SETUID`` - 자식의 실행 사용자 ID를 ``uv_process_options_t.uid``로
  설정합니다.
* ``UV_PROCESS_SETGID`` - 자식의 실행 그룹 ID를 ``uv_process_options_t.gid``로
  설정합니다.

UID/GID 변경은 Unix에서만 지원되며, Windows에서 ``uv_spawn``은 ``UV_ENOTSUP``로
실패합니다.

* ``UV_PROCESS_WINDOWS_VERBATIM_ARGUMENTS`` - Windows에서 ``uv_process_options_t.args``의
  인용 또는 이스케이프가 수행되지 않습니다. Unix에서는 무시됩니다.
* ``UV_PROCESS_DETACHED`` - 새 세션에서 자식 프로세스를 시작하며, 부모 프로세스가
  종료된 후에도 계속 실행됩니다.

## Detaching processes

``UV_PROCESS_DETACHED`` 플래그를 전달하면 데몬 또는 부모와 독립적인 자식 프로세스를
시작하는 데 사용할 수 있으므로 부모가 종료되어도 영향을 받지 않습니다.

```c
// detach/main.c
// (코드 예제는 원본 참조)
```

핸들이 여전히 자식을 모니터링하고 있으므로 프로그램이 종료되지 않는다는 것을 기억하세요.
더 *발사 후 망각*하고 싶다면 ``uv_unref()``를 사용하세요.

## Sending signals to processes

libuv는 Unix에서 표준 ``kill(2)`` 시스템 호출을 래핑하고 Windows에서 유사한 의미를
가진 것을 구현합니다. *한 가지 주의사항*: ``SIGTERM``, ``SIGINT`` 및 ``SIGKILL`` 모두
프로세스 종료로 이어집니다. ``uv_kill``의 시그니처:

```c
uv_err_t uv_kill(int pid, int signum);
```

libuv를 사용하여 시작된 프로세스의 경우 대신 ``uv_process_kill``을 사용할 수 있으며,
이것은 pid 대신 ``uv_process_t`` 감시자를 첫 번째 인수로 받습니다. 이 경우 **종료
콜백이 호출된 _후_ 감시자에서 ``uv_close``를 호출하는 것을 기억하세요**.

## Signals

libuv는 `일부 Windows 지원 <http://docs.libuv.org/en/v1.x/signal.html#signal>`_과
함께 Unix 시그널 주변의 래퍼를 제공합니다.

핸들을 초기화하고 루프와 연결하려면 ``uv_signal_init()``을 사용합니다. 해당 핸들러에서
특정 시그널을 수신하려면 핸들러 함수와 함께 ``uv_signal_start()``를 사용합니다. 각
핸들러는 하나의 시그널 번호와만 연결될 수 있으며, ``uv_signal_start()``에 대한 후속
호출은 이전 연결을 덮어씁니다. 감시를 중지하려면 ``uv_signal_stop()``을 사용합니다.
다양한 가능성을 보여주는 작은 예:

```c
// signal/main.c
// (코드 예제는 원본 참조)
```

프로세스에 ``SIGUSR1``을 보내면 각 ``uv_signal_t``에 대해 한 번씩 핸들러가 4번 호출되는
것을 볼 수 있습니다. 핸들러는 각 핸들을 중지하므로 프로그램이 종료됩니다. 이러한 종류의
모든 핸들러로의 디스패치는 매우 유용합니다. 여러 이벤트 루프를 사용하는 서버는 모든 루프가
``SIGINT``에 대한 감시자를 추가함으로써 종료 전에 모든 데이터가 안전하게 저장되었는지
확인할 수 있습니다.

## Child Process I/O

일반적인 새로 생성된 프로세스는 자체 파일 디스크립터 세트를 가지며, 0, 1, 2는 각각
``stdin``, ``stdout`` 및 ``stderr``입니다. 때로는 자식과 파일 디스크립터를 공유하고
싶을 수 있습니다. 예를 들어, 애플리케이션이 하위 명령을 시작하고 오류를 로그 파일로
보내고 싶지만 ``stdout``은 무시하고 싶을 수 있습니다. 이 경우 자식의 ``stderr``가
부모의 stderr와 동일하기를 원합니다. 이 경우 libuv는 파일 디스크립터 *상속*을 지원합니다.

자식 프로세스의 파일 디스크립터는 ``uv_process_options_t``의 ``stdio`` 필드를 사용하여
설정됩니다. 먼저 설정되는 파일 디스크립터 수에 ``stdio_count`` 필드를 설정합니다.
``uv_process_options_t.stdio``는 ``uv_stdio_container_t``의 배열이며:

```c
typedef struct uv_stdio_container_s {
    uv_stdio_flags flags;

    union {
        uv_stream_t* stream;
        int fd;
    } data;
} uv_stdio_container_t;
```

여기서 flags는 여러 값을 가질 수 있습니다. 사용되지 않을 경우 ``UV_IGNORE``를 사용합니다.
처음 세 ``stdio`` 필드가 ``UV_IGNORE``로 표시되면 ``/dev/null``로 리디렉션됩니다.

기존 디스크립터를 전달하려면 ``UV_INHERIT_FD``를 사용합니다. 그런 다음 ``fd``를
``stderr``로 설정합니다.

스트림에 이 리디렉션을 적용하는 것은 매우 간단합니다. ``flags``를 ``UV_INHERIT_STREAM``으로
설정하고 ``data.stream``을 부모 프로세스의 스트림으로 설정하면 자식 프로세스가 해당
스트림을 표준 I/O로 취급할 수 있습니다. 이것은 CGI_와 같은 것을 구현하는 데 사용할
수 있습니다.

.. _CGI: https://en.wikipedia.org/wiki/Common_Gateway_Interface

## Parent-child IPC

부모와 자식은 ``uv_stdio_container_t.flags``를 ``UV_CREATE_PIPE``와 ``UV_READABLE_PIPE``
또는 ``UV_WRITABLE_PIPE``의 비트 조합으로 설정하여 생성된 파이프를 통해 단방향 또는
양방향 통신을 가질 수 있습니다. 읽기/쓰기 플래그는 자식 프로세스의 관점에서입니다. 이 경우
``uv_stream_t* stream`` 필드는 초기화되었지만 열리지 않은 ``uv_pipe_t`` 인스턴스를
가리키도록 설정되어야 합니다.

## Arbitrary process IPC

도메인 소켓은 잘 알려진 이름과 파일 시스템의 위치를 가질 수 있으므로 관련 없는 프로세스
간 IPC에 사용할 수 있습니다. 오픈 소스 데스크톱 환경에서 사용하는 D-BUS_ 시스템은 이벤트
알림을 위해 도메인 소켓을 사용합니다. 그러면 다양한 애플리케이션이 연락처가 온라인 상태가
되거나 새 하드웨어가 감지될 때 반응할 수 있습니다. MySQL 서버도 클라이언트가 상호 작용할
수 있는 도메인 소켓을 실행합니다.

.. _D-BUS: https://www.freedesktop.org/wiki/Software/dbus

도메인 소켓을 사용할 때 일반적으로 클라이언트-서버 패턴이 따르며 소켓의 생성자/소유자가
서버 역할을 합니다. 초기 설정 후 메시징은 TCP와 다르지 않으므로 echo 서버 예제를 재사용합니다.

## Sending file descriptors over pipes

도메인 소켓의 멋진 점은 파일 디스크립터를 도메인 소켓을 통해 전송하여 프로세스 간에 교환할
수 있다는 것입니다. 이것은 프로세스가 I/O를 다른 프로세스에 넘길 수 있게 합니다. 애플리케이션에는
로드 밸런싱 서버, 워커 프로세스 및 CPU를 최적으로 사용하는 다른 방법이 포함됩니다. libuv는
현재 파이프를 통해 **TCP 소켓 또는 기타 파이프**만 전송하는 것을 지원합니다.

이를 시연하기 위해 라운드 로빈 방식으로 클라이언트를 워커 프로세스에 넘기는 echo 서버 구현을
살펴봅니다. 이 프로그램은 약간 복잡하며 책에는 스니펫만 포함되어 있지만, 정말 이해하려면
전체 코드를 읽는 것이 좋습니다.

워커 프로세스는 마스터가 파일 디스크립터를 넘겨주기 때문에 매우 간단합니다.

```c
// multi-echo-server/worker.c
// (코드 예제는 원본 참조)
```

``queue``는 다른 쪽 끝에 마스터 프로세스에 연결된 파이프이며, 새로운 파일 디스크립터가
전송됩니다. 이 파이프가 프로세스 간 통신에 사용될 것임을 나타내기 위해 ``uv_pipe_init``의
``ipc`` 인수를 1로 설정하는 것이 중요합니다! 마스터가 워커의 표준 입력에 파일 핸들을
쓰기 때문에 ``uv_pipe_open``을 사용하여 파이프를 ``stdin``에 연결합니다.

먼저 ``uv_pipe_pending_count()``를 호출하여 읽을 핸들을 사용할 수 있는지 확인합니다.
프로그램이 다른 유형의 핸들을 처리할 수 있는 경우 ``uv_pipe_pending_type()``을 사용하여
유형을 결정할 수 있습니다. 이 코드에서 ``accept``가 이상해 보이지만 실제로는 의미가
있습니다. ``accept``가 전통적으로 하는 것은 다른 파일 디스크립터(리스닝 소켓)에서 파일
디스크립터(클라이언트)를 가져오는 것입니다. 이것이 바로 여기서 하는 일입니다. ``queue``에서
파일 디스크립터(``client``)를 가져옵니다. 이 시점부터 워커는 표준 echo 서버 작업을 수행합니다.

이제 마스터로 돌아가서 로드 밸런싱을 허용하기 위해 워커가 시작되는 방법을 살펴봅니다.

```c
// multi-echo-server/main.c
// (코드 예제는 원본 참조)
```

``child_worker`` 구조는 프로세스와 마스터와 개별 프로세스 사이의 파이프를 래핑합니다.

워커 설정에서 libuv 함수 ``uv_cpu_info``를 사용하여 CPU 수를 얻어 동일한 수의 워커를
시작할 수 있습니다. 다시 IPC 채널 역할을 하는 파이프를 세 번째 인수를 1로 초기화하는
것이 중요합니다. 그런 다음 자식 프로세스의 ``stdin``이 (자식의 관점에서) 읽을 수 있는
파이프가 되도록 표시합니다. 여기까지는 모든 것이 간단합니다. 워커가 시작되고 표준 입력에
파일 디스크립터가 쓰여지기를 기다립니다.

``on_new_connection``(TCP 인프라는 ``main()``에서 초기화됨)에서 클라이언트 소켓을
수락하고 라운드 로빈의 다음 워커로 전달합니다.

``uv_write2`` 호출은 모든 추상화를 처리하며 핸들(``client``)을 올바른 인수로 전달하는
것만으로 충분합니다. 이것으로 다중 프로세스 echo 서버가 작동합니다.

``uv_write2()``가 핸들을 보낼 때도 비어 있지 않은 버퍼가 필요하다는 것을 지적한 Kyle에게
감사합니다.
