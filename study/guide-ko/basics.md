# Basics of libuv

libuv는 **비동기**, **이벤트 기반** 프로그래밍 스타일을 강제합니다. 핵심 작업은 이벤트 루프와
I/O 및 기타 활동에 대한 콜백 기반 알림을 제공하는 것입니다. libuv는 타이머, 논블로킹 네트워킹
지원, 비동기 파일 시스템 접근, 자식 프로세스 등의 핵심 유틸리티를 제공합니다.

## Event loops

이벤트 기반 프로그래밍에서 애플리케이션은 특정 이벤트에 관심을 표현하고 발생할 때 응답합니다.
운영 체제에서 이벤트를 수집하거나 다른 이벤트 소스를 모니터링하는 책임은 libuv가 처리하며,
사용자는 이벤트가 발생할 때 호출될 콜백을 등록할 수 있습니다. 이벤트 루프는 일반적으로
*영원히* 실행됩니다. 의사코드로:

```python
while there are still events to process:
    e = get the next event
    if there is a callback associated with e:
        call the callback
```

이벤트의 예:

* 파일이 쓰기 준비됨
* 소켓에 읽을 데이터가 준비됨
* 타이머가 만료됨

이 이벤트 루프는 ``uv_run()``으로 캡슐화됩니다. 이것이 libuv를 사용할 때의 최종 함수입니다.

시스템 프로그램의 가장 일반적인 활동은 많은 수치 계산보다는 입력과 출력을 다루는 것입니다.
기존 입출력 함수(``read``, ``fprintf`` 등)를 사용하는 문제는 **블로킹**이라는 점입니다.
하드 디스크에 실제로 쓰거나 네트워크에서 읽는 것은 프로세서 속도에 비해 불균형적으로 오래
걸립니다. 함수는 작업이 완료될 때까지 반환하지 않으므로 프로그램은 아무것도 하지 않습니다.
고성능이 필요한 프로그램의 경우 다른 활동과 다른 I/O 작업이 대기하게 되므로 이것은 주요
장애물입니다.

표준 솔루션 중 하나는 스레드를 사용하는 것입니다. 각 블로킹 I/O 작업은 별도의 스레드(또는
스레드 풀)에서 시작됩니다. 블로킹 함수가 스레드에서 호출되면 운영 체제는 실제로 CPU가 필요한
다른 스레드를 실행하도록 스케줄링할 수 있습니다.

libuv가 따르는 접근 방식은 **비동기, 논블로킹** 스타일이라는 다른 스타일을 사용합니다.
대부분의 현대 운영 체제는 이벤트 알림 하위 시스템을 제공합니다. 예를 들어, 소켓에 대한 일반적인
``read`` 호출은 송신자가 실제로 무언가를 보낼 때까지 블로킹됩니다. 대신 애플리케이션은 운영
체제에 소켓을 감시하고 큐에 이벤트 알림을 넣도록 요청할 수 있습니다. 애플리케이션은 편의에 따라
이벤트를 검사할 수 있고(아마도 프로세서를 최대한 활용하기 위해 일부 수치 계산을 먼저 수행한 후)
데이터를 가져올 수 있습니다. 애플리케이션이 한 지점에서 관심을 표현한 다음 다른 지점(시간과
공간에서)에서 데이터를 사용하기 때문에 **비동기**입니다. 애플리케이션 프로세스가 다른 작업을
자유롭게 수행할 수 있었기 때문에 **논블로킹**입니다. 이것은 운영 체제 이벤트를 또 다른 libuv
이벤트로 취급할 수 있기 때문에 libuv의 이벤트 루프 접근 방식에 잘 맞습니다. 논블로킹은 다른
이벤트가 들어오는 속도만큼 빠르게 계속 처리될 수 있도록 보장합니다.

.. NOTE::

    I/O가 백그라운드에서 실행되는 방식은 우리의 관심사가 아니지만, 스레드가 프로세서의 기본
    단위인 컴퓨터 하드웨어 작동 방식으로 인해 libuv와 OS는 일반적으로 백그라운드/워커 스레드
    및/또는 폴링을 실행하여 논블로킹 방식으로 작업을 수행합니다.

libuv 핵심 개발자 중 한 명인 Bert Belder는 libuv의 아키텍처와 배경을 설명하는 작은
비디오가 있습니다. libuv나 libev에 대한 사전 경험이 없다면 빠르고 유용한 시청입니다.

libuv의 이벤트 루프는 `문서
<https://docs.libuv.org/en/v1.x/design.html#the-i-o-loop>`_에서 더 자세히 설명됩니다.

## Hello World

기본 사항을 마쳤으니 첫 번째 libuv 프로그램을 작성해봅시다. 루프를 시작하지만 즉시 종료되는
것 외에는 아무것도 하지 않습니다.

```c
// helloworld/main.c
#include <stdio.h>
#include <stdlib.h>
#include <uv.h>

int main() {
    uv_loop_t *loop = malloc(sizeof(uv_loop_t));
    uv_loop_init(loop);

    printf("Now quitting.\n");
    uv_run(loop, UV_RUN_DEFAULT);

    uv_loop_close(loop);
    free(loop);
    return 0;
}
```

이 프로그램은 처리할 이벤트가 없기 때문에 즉시 종료됩니다. libuv 이벤트 루프는 다양한 API
함수를 사용하여 이벤트를 감시하도록 지시받아야 합니다.

libuv v1.0부터 사용자는 ``uv_loop_init(uv_loop_t *)``로 초기화하기 전에 루프에 대한
메모리를 할당해야 합니다. 이를 통해 사용자 정의 메모리 관리를 연결할 수 있습니다. ``uv_loop_close(uv_loop_t *)``를
사용하여 루프를 비초기화한 다음 스토리지를 삭제하는 것을 기억하세요. 예제는 루프가 끝난 후
프로그램이 종료되고 시스템이 메모리를 회수하므로 루프를 닫지 않습니다. 프로덕션 등급 프로젝트,
특히 장기 실행 시스템 프로그램은 올바르게 해제하는 데 주의해야 합니다.

### Default loop

libuv는 ``uv_default_loop()``를 사용하여 액세스할 수 있는 기본 루프를 제공합니다.
단일 루프만 원하는 경우 이 루프를 사용해야 합니다.

```c
// default-loop/main.c
#include <stdio.h>
#include <uv.h>

int main() {
    uv_loop_t *loop = uv_default_loop();

    printf("Default loop.\n");
    uv_run(loop, UV_RUN_DEFAULT);

    uv_loop_close(loop);
    return 0;
}
```

.. note::

    node.js는 기본 루프를 메인 루프로 사용합니다. 바인딩을 작성하는 경우 이를 인식해야 합니다.

## Error handling

실패할 수 있는 초기화 함수 또는 동기 함수는 오류 시 음수를 반환합니다. 실패할 수 있는 비동기
함수는 콜백에 상태 매개변수를 전달합니다. 오류 메시지는 ``UV_E*`` `상수`_로 정의됩니다.

.. _constants: https://docs.libuv.org/en/v1.x/errors.html#error-constants

``uv_strerror(int)`` 및 ``uv_err_name(int)`` 함수를 사용하여 각각 오류를 설명하는
``const char *`` 또는 오류 이름을 얻을 수 있습니다.

I/O 읽기 콜백(파일 및 소켓용)은 ``nread`` 매개변수를 전달받습니다. ``nread``가 0보다
작으면 오류가 발생한 것입니다(UV_EOF는 파일 끝 오류이며 다르게 처리할 수 있습니다).

## Handles and Requests

libuv는 사용자가 특정 이벤트에 관심을 표현함으로써 작동합니다. 이것은 일반적으로 I/O 장치,
타이머 또는 프로세스에 대한 **핸들**을 생성하여 수행됩니다. 핸들은 불투명한 구조체이며
``uv_TYPE_t``로 명명되며 여기서 type은 핸들이 사용되는 용도를 나타냅니다.

핸들은 장기 실행 객체를 나타냅니다. 이러한 핸들에 대한 비동기 작업은 **요청**을 사용하여
식별됩니다. 요청은 수명이 짧고(일반적으로 하나의 콜백에서만 사용됨) 일반적으로 핸들에 대한
하나의 I/O 작업을 나타냅니다. 요청은 개별 작업의 시작과 콜백 사이의 컨텍스트를 보존하는 데
사용됩니다. 예를 들어, UDP 소켓은 ``uv_udp_t``로 표현되는 반면, 소켓에 대한 개별 쓰기는
작성이 완료된 후 콜백에 전달되는 ``uv_udp_send_t`` 구조를 사용합니다.

핸들은 해당 함수로 설정됩니다::

    uv_TYPE_init(uv_loop_t *, uv_TYPE_t *)

콜백은 감시자가 관심 있는 이벤트가 발생할 때마다 libuv가 호출하는 함수입니다. 애플리케이션
특정 로직은 일반적으로 콜백에서 구현됩니다. 예를 들어, IO 감시자의 콜백은 파일에서 읽은
데이터를 받고, 타이머 콜백은 타임아웃 시 트리거됩니다.

## Idling

다음은 idle 핸들을 사용하는 예입니다. 콜백은 이벤트 루프가 돌 때마다 한 번 호출됩니다.
idle 핸들의 사용 사례는 :doc:`utilities`에서 논의됩니다. idle 감시자를 사용하여 감시자
생명주기를 살펴보고 감시자가 있기 때문에 ``uv_run()``이 이제 블로킹되는 방법을 봅시다.
카운트에 도달하면 idle 감시자가 중지되고 활성 이벤트 감시자가 없기 때문에 ``uv_run()``이
종료됩니다.

```c
// idle-basic/main.c
#include <stdio.h>
#include <uv.h>

int64_t counter = 0;

void wait_for_a_while(uv_idle_t* handle) {
    counter++;

    if (counter >= 10e6)
        uv_idle_stop(handle);
}

int main() {
    uv_idle_t idler;

    uv_idle_init(uv_default_loop(), &idler);
    uv_idle_start(&idler, wait_for_a_while);

    printf("Idling...\n");
    uv_run(uv_default_loop(), UV_RUN_DEFAULT);

    uv_loop_close(uv_default_loop());
    return 0;
}
```

## Storing context

콜백 기반 프로그래밍 스타일에서 호출 사이트와 콜백 사이에 일부 '컨텍스트'(애플리케이션 특정
정보)를 전달하고 싶을 때가 많습니다. 모든 핸들과 요청에는 컨텍스트로 설정하고 콜백에서 다시
캐스팅할 수 있는 ``void* data`` 멤버가 있습니다. 이것은 C 라이브러리 생태계 전반에 걸쳐
사용되는 일반적인 패턴입니다. 또한 ``uv_loop_t``도 유사한 데이터 멤버를 가지고 있습니다.
