# Threads

잠깐, 왜 스레드인가요? 이벤트 루프가 *웹 규모 프로그래밍*을 하는 **방법**이 아닌가요?
음... 아닙니다. 스레드는 여전히 프로세서가 작업을 수행하는 매체입니다. 따라서 다양한
동기화 프리미티브를 헤쳐나가야 할 수도 있지만 스레드는 때때로 매우 유용합니다.

스레드는 내부적으로 모든 시스템 호출의 비동기 특성을 모방하는 데 사용됩니다. libuv는 또한
스레드를 생성하고 완료되면 결과를 수집하여 애플리케이션인 여러분이 실제로 블로킹되는 작업을
비동기적으로 수행할 수 있도록 스레드를 사용합니다.

오늘날 두 가지 주요 스레드 라이브러리가 있습니다: Windows 스레드 구현과 POSIX의
:man:`pthreads(7)`. libuv의 스레드 API는 pthreads API와 유사하며 종종 유사한 의미를
가집니다.

libuv의 스레드 시설의 주목할 만한 측면은 libuv 내에서 자체 포함된 섹션이라는 것입니다.
다른 기능이 이벤트 루프와 콜백 원칙에 밀접하게 의존하는 반면, 스레드는 완전히 무관하며
필요에 따라 블로킹하고 반환 값을 통해 오류를 직접 신호하며, :ref:`첫 번째 예제 <thread-create-example>`에서
보여주듯이 실행 중인 이벤트 루프도 필요하지 않습니다.

libuv의 스레드 API는 또한 매우 제한적입니다. 스레드의 의미와 구문이 모든 플랫폼에서
다르고 완전성 수준이 다르기 때문입니다.

이 장은 다음 가정을 합니다: **하나의 이벤트 루프만 있으며, 하나의 스레드(메인 스레드)에서
실행됩니다**. 다른 스레드는 이벤트 루프와 상호 작용하지 않습니다(``uv_async_send``를
사용하는 경우 제외).

## Core thread operations

여기에는 많은 것이 없습니다. ``uv_thread_create()``를 사용하여 스레드를 시작하고
``uv_thread_join()``을 사용하여 닫힐 때까지 기다립니다.

```c
// thread-create/main.c
// (코드 예제는 원본 참조)
```

.. tip::

    ``uv_thread_t``는 Unix에서 ``pthread_t``의 별칭일 뿐이지만 이것은 구현 세부사항이며
    항상 사실일 것이라고 의존하지 마세요.

두 번째 매개변수는 스레드의 진입점 역할을 할 함수이고, 마지막 매개변수는 스레드에 사용자
정의 매개변수를 전달하는 데 사용할 수 있는 ``void *`` 인수입니다. ``hare`` 함수는 이제
운영 체제에 의해 선점적으로 스케줄링되는 별도의 스레드에서 실행됩니다.

``pthread_join()``과 달리 대상 스레드가 두 번째 매개변수를 사용하여 호출 스레드로 값을
전달할 수 있게 하는 ``uv_thread_join()``은 그렇지 않습니다. 값을 보내려면
:ref:`스레드 간 통신 <inter-thread-communication>`을 사용하세요.

## Synchronization Primitives

이 섹션은 의도적으로 간결합니다. 이 책은 스레드에 관한 것이 아니므로 여기서는 libuv API의
놀라운 점만 나열합니다. 나머지는 :man:`pthreads(7)` man 페이지를 참조할 수 있습니다.

### Mutexes

뮤텍스 함수는 pthread 동등물에 대한 **직접** 매핑입니다.

```c
int uv_mutex_init(uv_mutex_t* handle);
int uv_mutex_init_recursive(uv_mutex_t* handle);
void uv_mutex_destroy(uv_mutex_t* handle);
void uv_mutex_lock(uv_mutex_t* handle);
int uv_mutex_trylock(uv_mutex_t* handle);
void uv_mutex_unlock(uv_mutex_t* handle);
```

``uv_mutex_init()``, ``uv_mutex_init_recursive()`` 및 ``uv_mutex_trylock()``
함수는 성공 시 0을 반환하고 그렇지 않으면 오류 코드를 반환합니다.

`libuv`가 디버깅이 활성화된 상태로 컴파일된 경우 ``uv_mutex_destroy()``,
``uv_mutex_lock()`` 및 ``uv_mutex_unlock()``은 오류 시 ``abort()``합니다.
마찬가지로 ``uv_mutex_trylock()``은 오류가 ``EAGAIN`` 또는 ``EBUSY`` *이외*인 경우
중단합니다.

재귀적 뮤텍스가 지원되지만 의존하지 마세요. 또한 ``uv_cond_t`` 변수와 함께 사용하지
마세요.

기본 BSD 뮤텍스 구현은 뮤텍스를 잠근 스레드가 다시 잠그려고 시도하면 오류를 발생시킵니다.
예를 들어:

```c
uv_mutex_init(a_mutex);
uv_mutex_lock(a_mutex);
uv_thread_create(thread_id, entry, (void *)a_mutex);
uv_mutex_lock(a_mutex);
// 여기에 더 많은 것들
```

다른 스레드가 일부 작업을 초기화한 다음 ``a_mutex``를 잠금 해제할 때까지 기다리는 데
사용할 수 있지만 디버그 모드에서 프로그램이 충돌하거나 ``uv_mutex_lock()``의 두 번째
호출에서 오류를 반환합니다.

.. note::

    Windows의 뮤텍스는 항상 재귀적입니다.

### Locks

읽기-쓰기 잠금은 더 세분화된 액세스 메커니즘입니다. 두 명의 독자가 동시에 공유 메모리에
액세스할 수 있습니다. 작성자는 독자가 보유하고 있을 때 잠금을 획득할 수 없습니다. 독자
또는 작성자는 작성자가 보유하고 있을 때 잠금을 획득할 수 없습니다. 읽기-쓰기 잠금은
데이터베이스에서 자주 사용됩니다. 다음은 장난감 예제입니다.

```c
// locks/main.c - simple rwlocks
// (코드 예제는 원본 참조)
```

이것을 실행하고 독자가 때때로 겹치는 것을 관찰하세요. 여러 작성자의 경우 스케줄러는
일반적으로 더 높은 우선순위를 부여하므로 두 명의 작성자를 추가하면 두 작성자가 모두
독자가 다시 기회를 얻기 전에 먼저 완료되는 경향이 있음을 볼 수 있습니다.

위 예제에서 배리어도 사용하므로 메인 스레드가 모든 독자와 작성자가 종료되었음을 나타낼
때까지 기다릴 수 있습니다.

### Others

libuv는 또한 pthread 대응물과 매우 유사한 API로 세마포어_, `조건 변수`_ 및 배리어_를
지원합니다.

.. _semaphores: https://en.wikipedia.org/wiki/Semaphore_(programming)
.. _condition variables: https://en.wikipedia.org/wiki/Monitor_(synchronization)#Condition_variables_2
.. _barriers: https://en.wikipedia.org/wiki/Barrier_(computer_science)

또한 libuv는 편의 함수 ``uv_once()``를 제공합니다. 여러 스레드가 주어진 가드와 함수
포인터로 ``uv_once()``를 호출하려고 시도할 수 있으며, **첫 번째 것만 승리하고 함수는
한 번만 호출됩니다**:

```c
/* 가드 초기화 */
static uv_once_t once_only = UV_ONCE_INIT;

int i = 0;

void increment() {
    i++;
}

void thread1() {
    /* ... 작업 */
    uv_once(once_only, increment);
}

void thread2() {
    /* ... 작업 */
    uv_once(once_only, increment);
}

int main() {
    /* ... 스레드 생성 */
}
```

모든 스레드가 완료된 후 ``i == 1``입니다.

libuv v0.11.11부터 ``uv_key_t`` 구조와 스레드 로컬 스토리지를 위한 api_도 추가되었습니다.

.. _api: http://docs.libuv.org/en/v1.x/threading.html#thread-local-storage

## libuv work queue

``uv_queue_work()``는 애플리케이션이 별도의 스레드에서 작업을 실행하고 작업이 완료될 때
트리거되는 콜백을 가질 수 있게 하는 편의 함수입니다. 겉보기에 간단한 함수인 ``uv_queue_work()``를
유혹하게 만드는 것은 잠재적으로 모든 타사 라이브러리를 이벤트 루프 패러다임과 함께 사용할
수 있게 한다는 것입니다. 이벤트 루프를 사용할 때 *루프 스레드에서 주기적으로 실행되는
함수가 I/O를 수행할 때 블로킹되지 않거나 심각한 CPU 부하가 아니라는 것을 확인하는 것이
필수적*입니다. 이것은 루프가 느려지고 이벤트가 전체 용량으로 처리되지 않는다는 것을
의미하기 때문입니다.

그러나 많은 기존 코드가 반응성을 원하는 경우 스레드와 함께 사용할 블로킹 함수(예: 내부적으로
I/O를 수행하는 루틴)를 특징으로 합니다(클래식 '클라이언트당 하나의 스레드' 서버 모델).
그리고 이벤트 루프 라이브러리와 함께 작동하도록 만드는 것은 일반적으로 별도의 스레드에서
작업을 실행하는 자체 시스템을 구축하는 것을 포함합니다. libuv는 이것에 대한 편리한
추상화를 제공합니다.

다음은 `node.js is cancer`_에서 영감을 받은 간단한 예입니다. 피보나치 수를 계산하고
그 과정에서 조금 잠을 자지만 별도의 스레드에서 실행하여 블로킹 및 CPU 바인딩 작업이 이벤트
루프가 다른 활동을 수행하는 것을 방지하지 않도록 합니다.

```c
// queue-work/main.c - lazy fibonacci
// (코드 예제는 원본 참조)
```

실제 작업 함수는 간단하며 별도의 스레드에서 실행될 것임을 보여주는 것은 없습니다.
``uv_work_t`` 구조가 단서입니다. ``void* data`` 필드를 사용하여 임의의 데이터를 통해
전달하고 스레드와 통신하는 데 사용할 수 있습니다. 하지만 두 스레드가 모두 실행되는 동안
변경하는 경우 적절한 잠금을 사용하는지 확인하세요.

트리거는 ``uv_queue_work``입니다:

```c
// queue-work/main.c
// (코드 예제는 원본 참조)
```

스레드 함수는 별도의 스레드에서 시작되며 ``uv_work_t`` 구조를 전달받고 함수가 반환되면
*after* 함수가 이벤트 루프가 실행되는 스레드에서 호출됩니다. 동일한 구조가 전달됩니다.

블로킹 라이브러리에 대한 래퍼를 작성하기 위해 일반적인 :ref:`패턴 <baton>`은 데이터를
교환하기 위해 배턴을 사용하는 것입니다.

libuv 버전 `0.9.4`부터 추가 함수 ``uv_cancel()``이 사용 가능합니다. 이것은 libuv
작업 큐의 작업을 취소할 수 있게 합니다. *아직 시작되지 않은* 작업만 취소할 수 있습니다.
작업이 *이미 실행을 시작했거나 실행을 완료한* 경우 ``uv_cancel()``은 **실패**합니다.

``uv_cancel()``은 사용자가 종료를 요청할 때 보류 중인 작업을 정리하는 데 유용합니다.
예를 들어, 음악 플레이어는 오디오 파일을 스캔하기 위해 여러 디렉토리를 큐에 넣을 수
있습니다. 사용자가 프로그램을 종료하면 빠르게 종료하고 모든 보류 중인 요청이 실행될 때까지
기다리지 않아야 합니다.

피보나치 예제를 수정하여 ``uv_cancel()``을 시연합시다. 먼저 종료를 위한 시그널 핸들러를
설정합니다.

```c
// queue-cancel/main.c
// (코드 예제는 원본 참조)
```

사용자가 ``Ctrl+C``를 눌러 시그널을 트리거하면 모든 워커에 ``uv_cancel()``을 보냅니다.
``uv_cancel()``은 실행 대기 중이고 취소할 수 있는 작업에 대해 ``0``을 반환합니다.

성공적으로 취소되는 작업의 경우 *after* 함수는 ``status``가 ``UV_ECANCELED``로 설정된
상태로 호출됩니다.

``uv_cancel()``은 ``uv_fs_t`` 및 ``uv_getaddrinfo_t`` 요청과 함께 사용할 수도 있습니다.
파일 시스템 함수 제품군의 경우 ``uv_fs_t.errorno``가 ``UV_ECANCELED``로 설정됩니다.

.. TIP::

    잘 설계된 프로그램은 이미 실행을 시작한 장기 실행 워커를 종료하는 방법이 있어야 합니다.
    이러한 워커는 종료를 신호하기 위해 메인 프로세스만 설정하는 변수를 주기적으로 확인할
    수 있습니다.

## Inter-thread communication

때로는 실행 *중*에 다양한 스레드가 실제로 서로 메시지를 보내고 싶을 수 있습니다. 예를 들어
별도의 스레드에서 일부 장기 작업을 실행하고(아마도 ``uv_queue_work``를 사용하여) 메인
스레드에 진행 상황을 알리고 싶을 수 있습니다. 이것은 실행 중인 다운로드의 상태를 사용자에게
알리는 다운로드 관리자를 가진 간단한 예입니다.

```c
// progress/main.c
// (코드 예제는 원본 참조)
```

비동기 스레드 통신은 *루프*에서 작동하므로 모든 스레드가 메시지 발신자가 될 수 있지만
libuv 루프가 있는 스레드만 수신자가 될 수 있습니다(또는 루프가 수신자입니다). libuv는
메시지를 받을 때마다 비동기 감시자와 함께 콜백(``print_progress``)을 호출합니다.

.. warning::

    메시지 전송이 *비동기*이므로 콜백이 다른 스레드에서 ``uv_async_send``가 호출된 직후
    호출될 수 있거나 일정 시간 후에 호출될 수 있다는 것을 인식하는 것이 중요합니다.
    libuv는 또한 ``uv_async_send``에 대한 여러 호출을 결합하고 콜백을 한 번만 호출할
    수 있습니다. libuv가 보장하는 유일한 것은 -- 콜백 함수가 ``uv_async_send`` 호출
    *후* *최소한 한 번* 호출된다는 것입니다. ``uv_async_send``에 대한 보류 중인 호출이
    없으면 콜백이 호출되지 않습니다. 두 번 이상 호출하고 libuv가 아직 콜백을 실행할
    기회가 없다면 여러 ``uv_async_send`` 호출에 대해 콜백을 *한 번만* 호출할 *수*
    있습니다. 하나의 이벤트에 대해 콜백이 두 번 호출되지 않습니다.

다운로드 함수에서 진행 표시기를 수정하고 ``uv_async_send``로 메시지를 전달하기 위해
큐에 넣습니다. 기억하세요: ``uv_async_send``는 논블로킹이며 즉시 반환합니다.

콜백은 감시자에서 데이터를 추출하는 표준 libuv 패턴입니다.

마지막으로 감시자를 정리하는 것을 기억하는 것이 중요합니다.

이 예제 후에 ``data`` 필드의 남용을 보여준 후, bnoordhuis_는 ``data`` 필드를 사용하는
것이 스레드 안전하지 않으며 ``uv_async_send()``는 실제로 이벤트 루프를 깨우는 것만
의도되었다고 지적했습니다. 액세스가 올바른 순서로 수행되도록 뮤텍스 또는 rwlock을 사용하세요.

.. note::

    뮤텍스와 rwlocks는 시그널 핸들러 내에서 작동하지 **않지만** ``uv_async_send``는
    작동합니다.

``uv_async_send``가 필요한 한 가지 사용 사례는 기능에 스레드 친화성이 필요한 라이브러리와
상호 운용하는 것입니다. 예를 들어 node.js에서 v8 엔진 인스턴스, 컨텍스트 및 해당 객체는
v8 인스턴스가 시작된 스레드에 바인딩됩니다. 다른 스레드에서 v8 데이터 구조와 상호 작용하면
정의되지 않은 결과가 발생할 수 있습니다. 이제 타사 라이브러리를 바인딩하는 일부 node.js
모듈을 고려하세요. 다음과 같이 진행될 수 있습니다:

1. node에서 타사 라이브러리는 더 많은 정보에 대해 호출될 JavaScript 콜백으로 설정됩니다.
2. ``lib.do``는 논블로킹이어야 하지만 타사 lib는 블로킹이므로 바인딩은 ``uv_queue_work``를
   사용합니다.
3. 별도의 스레드에서 수행되는 실제 작업은 진행 콜백을 호출하고 싶지만 JavaScript와
   상호 작용하기 위해 v8에 직접 호출할 수 없습니다. 그래서 ``uv_async_send``를 사용합니다.
4. 메인 루프 스레드에서 호출되는 비동기 콜백은 v8 스레드이며, 그런 다음 v8과 상호 작용하여
   JavaScript 콜백을 호출합니다.
